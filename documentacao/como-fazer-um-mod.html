Como fazer um mod

Um mod é uma pasta com um manifest.json e, dentro dela, arquivos JSON de conteúdo. Pode também trazer imagens PNG, modelos .bbmodel (Blockbench), sons WAV e scripts em JavaScript (pasta scripts/).

A maior parte de um mod é dados: item, máquina, receita, pesquisa e inimigo novos não precisam de código. Quando precisa de um comportamento que o JSON não tem (uma máquina que reage ao jogador, uma janela própria, peças girando, eventos), o mod traz um script. Os scripts rodam só no servidor, trancados: sem acesso aos seus arquivos, à internet ou ao resto do computador, com limite de memória e de tempo (veja Scripts).

O jogo base é carregado pelo mesmo sistema: tudo o que mods/base faz, um mod também pode fazer.

O jeito mais rápido de começar é o botão Criar mod (Menu → Mods): você dá um nome e o jogo monta a pasta com um item, uma máquina com script (uma prensa que faz peças) e a janela dela, o mekzorio.d.ts para o VS Code completar e um LEIA-ME.txt com os próximos passos — o mod já funciona do jeito que sai. Outro jeito é copiar um mod de exemplo e mudar o que quiser:

  • mods/fornalha_tijolos: o mais simples (item, construção com portas, receita, pesquisa, ícone, modelo e som);
  • mods/exemplo_destilaria: com líquidos (líquido novo, tanques, portas de cano, categoria de receita nova);
  • mods/mecanica_exemplo: com script (motor rotativo e caixa de engrenagem, peças girando, janela própria).

Esta página é o passo a passo. A lista completa de campos (cada tipo de construção, líquidos, veículos, módulos, pesquisas infinitas, regiões, plantas…) está em Campos do JSON.

Onde colocar

Pasta Para quê
mods/ (ao lado do jogo) Mods que vêm com o jogo: base e os exemplos.
Pasta dos seus mods Os seus mods e os que você baixar. No jogo, abra Menu → Mods → Abrir pasta dos meus mods. No Linux ela fica em ~/.local/share/godot/app_userdata/MEKZORIO/mods.

Depois de colocar o mod na pasta, vá em Menu → Mods, marque o mod e clique em Aplicar.

  • Se faltar uma dependência, ela é ativada sozinha quando está instalada.
  • Se algo estiver errado, o jogo mostra todos os erros, cada um com o arquivo e o motivo.

Se o mesmo mod (mesmo id) estiver nas duas pastas, vale a versão maior.

manifest.json

{
  "id": "meu_mod",                       // letras minúsculas, números e _ (até 48)
  "name": { "pt-BR": "Meu mod", "en": "My mod" },
  "version": "1.0.0",                    // sempre 3 números
  "authors": [ "Seu nome" ],
  "description": { "pt-BR": "O que o mod faz." },
  "gameVersion": ">=0.2.0",              // versões do jogo em que ele funciona
  "apiVersion": 1,                       // versão da API de mods (hoje 1; sem o campo, também 1)
  "dependencies": { "base": ">=0.2.0", "?outro_mod": "*" },
  "side": "both"
}

Coloque um icon.png (32×32, pixel art) ao lado do manifesto para ele aparecer na lista de mods.

Versões nas dependências

Uma dependência pode pedir uma versão exata ou uma faixa de versões:

Escreva Significa
* qualquer versão
1.2.3 ou =1.2.3 exatamente essa
>=1.2.0, >1.2.0, <=2.0.0, <2.0.0 maior/menor que
^1.2.0 1.2.0 ou mais nova, sem mudar o primeiro número (em 0.x, sem mudar o segundo)
~1.2.0 1.2.0 ou mais nova, sem mudar os dois primeiros números
>=1.0.0 <2.0.0 as duas condições juntas

Para o base (o próprio jogo), use >=: o ^0.1.0 recusa a 0.2.0, porque em 0.x o segundo número não pode mudar. Se o jogo disser "precisa de base ^0.1.0, mas a versão instalada é 0.2.0", troque para ">=0.1.0".

Um ? na frente do id ("?outro_mod") torna a dependência opcional: o seu mod carrega mesmo sem ela, mas, se ela estiver ativa, carrega antes do seu.

A ordem de carga é calculada sozinha: as dependências vêm antes, e o resto segue em ordem alfabética do id. Por isso a ordem é a mesma em qualquer computador.

Conteúdo (content/*.json)

Cada arquivo pode ter qualquer uma destas listas:

  • items
  • terrain
  • resources
  • buildings
  • recipes
  • research
  • contracts

Pode ter também worldgen e player, que normalmente só o base usa.

Comentários // e vírgula sobrando no fim são aceitos. Um campo com nome errado vira um erro, para não passar despercebido.

Ids: um id sem prefixo é do seu mod ("brick_furnace" vira meu_mod:brick_furnace). Para usar algo de outro mod, ponha o prefixo: "base:iron_plate".

Itens

{ "id": "tijolo_refratario", "name": { "pt-BR": "Tijolo refratário" }, "stackSize": 100, "color": "#b0563c", "fuel": 0 }
  • fuel: segundos que o item mantém uma máquina queimando. O carvão vale 20.
  • color: cor usada enquanto não há um ícone.

Construções

{
  "id": "brick_furnace", "item": "brick_furnace", "color": "#a4513a", "size": [ 2, 2 ],
  "crafter": { "category": "smelting", "fuel": true, "speed": 2 },
  "ports": [ { "x": 0, "y": 0, "side": "west", "type": "input" }, { "x": 1, "y": 0, "side": "east", "type": "output" } ]
}

Cada construção tem exatamente um comportamento. Os mais usados estão abaixo; a lista completa (reator, silo, bomba, canos, baterias, drones, trilhos, torreta…) está na referência:

Comportamento Campos (padrão)
belt (esteira) speed (1.875 itens/s por faixa), texture, rail
miner (mineradora) time (2 s por minério), fuel (true)
crafter (fornalha, montadora) category ou categories, fuel (true), selectRecipe (false), speed (1 = normal, 2 = o dobro; de 0.1 a 20)
container (baú) slots (16)
generator (gerador) output (kW), fuelRate (1)
pole (poste) reach (7 tiles: fio até outros postes e cabo até as máquinas)
lab (laboratório) slots (4)
inserter (braço) time (0.8 s por item)
splitter (divisor) buffer (2)
tunnel (subterrânea/aérea) range (5), speed, aerial (false)
  • Energia: "power": { "use": 90 } (kW) faz uma mineradora, montadora, laboratório ou braço usar eletricidade em vez de carvão. A máquina se liga sozinha, por cabo, ao poste mais perto dentro do alcance dele.
  • Portas: x, y são o tile dentro da construção, na orientação original (a frente é o leste). side é north, south, east ou west, e type é input ou output.

Receitas

{ "id": "brick_furnace", "category": "hand", "group": "energy", "time": 1.5,
  "inputs": { "base:stone_brick": 10 }, "outputs": { "brick_furnace": 1 } }

Categorias do jogo base:

Categoria Onde é feita
hand na mão e na montadora
smelting nas fornalhas (só 1 ingrediente)
assembling só na montadora

Uma categoria nova só funciona se alguma construção do mod a fizer.

O group é a aba da tela de fabricação (energy, logistics, science). Sem ele, a receita vai para a aba de produção.

Pesquisas

{ "id": "brick_furnace", "name": { "pt-BR": "Fornalha de tijolos" }, "description": { "pt-BR": "…" },
  "cost": { "base:automation_pack": 1 }, "units": 15, "time": 10,
  "prerequisites": [ "base:automation" ], "unlocks": [ "brick_furnace" ] }
  • cost: pacotes por unidade.
  • units: quantas unidades a pesquisa tem.
  • time: segundos por unidade.
  • units: 0: a pesquisa já vem concluída. Serve para organizar a árvore, como a Energia do jogo base.
  • unlocks: as receitas listadas aqui começam bloqueadas até a pesquisa terminar.
  • nodeOnly: true: nos mundos com a regra de progressão da Rede, o laboratório não pesquisa esse projeto. Um contrato precisa concedê-lo em rewardResearch; a conclusão libera diretamente suas receitas, sem cobrar pacotes. Não pode usar units: 0. Sem a regra (mundos antigos ou Sandbox), cost, units, time e pré-requisitos continuam definindo a pesquisa normal. Criativo continua com tudo liberado.

Um pré-requisito precisa ter sido carregado antes: num mod anterior ou mais acima no mesmo arquivo.

Contratos

{ "id": "tijolos", "name": { "pt-BR": "…" }, "item": "base:stone_brick", "perMinute": 20, "seconds": 120,
  "rewards": { "base:iron_plate": 50 }, "rewardResearch": [ "brick_furnace" ] }

Para um projeto exclusivo dos Nós, inclua nodeOnly: true na pesquisa e referencie seu ID em rewardResearch do último contrato da região. O carregador recusa um projeto exclusivo sem nenhum contrato que o libere. Confira se todos os materiais exigidos por esse contrato podem ser produzidos antes da liberação do projeto. Na primeira configuração do base: região 1 → eólica; 2 → solar; 3 → fundição elétrica; 4 → Automação 3. rewardResearch continua podendo conceder também pesquisas comuns, como já acontecia no Nó inicial.

Inimigos e MEKs

"enemies": [ { "id": "sentinela_blindada", "name": { "pt-BR": "Sentinela blindada" }, "ai": "sentinel",
               "health": 900, "damage": 9, "hitTime": 2, "speed": 10, "sight": 10, "leash": 28, "scrap": 4,
               "weight": 1, "model": "sentinela_blindada" } ]
  • ai: o comportamento, um dos que o jogo sabe fazer: sentinel (vigia a torre), warden (Guardião do Nó), mek (MEK de segurança do jogador), rogue_mek (MEK abandonado), scavenger (coletor de sucata), dismantler (desmontador), watcher (sentinela voadora).
  • Números: health, damage, hitTime (segundos por golpe), speed (sentinela = 17), sight e leash (tiles: até onde enxerga / até onde persegue), scrap (sucata ao cair). Os do jogo base estão em mods/base/content/enemies.json.
  • weight: com mais de um inimigo do mesmo ai, a torre sorteia entre eles por esse peso (0 = nunca aparece sozinho).
  • model: o .bbmodel (padrão: o próprio id; base:warden usa um do jogo). A animação work toca andando.

Recursos (jazidas) e terrenos

"resources": [ { "id": "estanho", "item": "estanho_minerio", "color": "#c8c8b4", "terrain": [ "base:rocky" ],
  "generation": { "scale": 40, "coverage": 0.02, "minAmount": 100, "maxAmount": 800, "starting": false } } ]

Scripts (JavaScript)

Exemplo completo e comentado: mods/mecanica_exemplo (motor rotativo + caixa de engrenagem: máquina nova, peças girando, janela própria). Referência completa de cada função: API dos scripts (gerada do jogo). Para o VS Code completar e explicar as funções enquanto você escreve, copie mekzorio.d.ts (vem com o jogo, na pasta mods) para a pasta scripts/ do seu mod.

Para comportamento que o jogo ainda não tem. O mod põe scripts/main.js (e outros .js que ele importar dessa pasta). O script roda só no servidor (no jogo sozinho, no servidor embutido): quem entra no servidor recebe só os dados e a arte do mod, nunca o .js.

import { events, world, players, storage, after, commands, console } from "mekzorio";

events.onPlayerJoin(p => players.message(p.id, `Bem-vindo, ${p.name}!`));
events.onCraft(c => { if (c.recipe === "base:iron_plate") storage.set("placas", (storage.get("placas") ?? 0) + 1); });
commands.register("placas", () => `Placas feitas desde o começo: ${storage.get("placas") ?? 0}`);
events.onTick(30 * 60, () => console.log("mais um minuto", world.tick));
Parte O que tem
events onTick(ticks, fn) (30 ticks = 1 s), onPlayerJoin, onPlayerLeave, onChat, onBuild, onRemove, onCraft, onResearch, onContract, onDeath, onRocketLaunch, onEnemyDefeated
world tick, seed, name, timeOfDay (0 = meia-noite), day, message(texto), tile(x, y), buildingAt(x, y), findBuildings({type, x, y, radius}), dropItems(x, y, item, n)
players list(), get(id), message(id, texto), teleport(id, x, y), give(id, item, n), take(id, item, n), count(id, item), isAdmin(id)
storage get(chave), set(chave, valor), delete(chave), keys() — salvo com o mundo (até 1 milhão de caracteres por mod)
commands register(nome, fn(jogador, args, texto), { admin, description }) → /nome no chat; o que fn devolve vai só para quem digitou
after(ticks, fn), random.int(min, max), console.log/warn/error Math.random tem semente (o mesmo em todo servidor)
buildings onTick(tipo, ticks, fn(b)), get(id), at(x, y), find({...}), build(tipo, x, y, rotação); e world.build/world.remove(id)
enemies spawn(tipo, x, y), get(id), list({...}), near(x, y, raio), types(), onTick(tipo, ticks, fn(e)), onDefeated(fn)

Máquina nova com script: no JSON, uma construção com um comportamento pronto (geralmente container, que dá os espaços de item que braços e esteiras usam) e "script": true — aí ela também pode ter "power". O script dá o trabalho:

buildings.onTick("meu_mod:prensa", 30, b => {
  b.wantsPower = true;                          // com "power": pede energia; b.power diz quanto chegou (0..1)
  if (b.power > 0.5 && b.count("iron_plate") >= 2) {
    b.extract("iron_plate", 2);                 // tira (some)
    b.insert("iron_gear", 1);                   // põe como um braço poria
    b.data.set("feitas", (b.data.get("feitas") ?? 0) + 1);   // dados desta máquina, salvos com o mundo
  }
});

Cada b tem: id, type, x, y, info (tudo de uma vez), working, power, enabled (false = a máquina para, qualquer uma), wantsPower, inventory, slots (entrada, combustível, saída, subproduto), fluids, count(item), insert(item, n), extract(item, n), addFluid(líquido, n), takeFluid(líquido, n), neighbors() (vizinhas com o lado), data.get/set/delete, remove(), animate(...) e pose(...) (abaixo).

Inimigos e MEKs pelo script: o inimigo novo vem do JSON (lista enemies, abaixo) e o comportamento dele é um dos 7 do jogo. O script cria, procura e dá ordens; com uma ordem, o comportamento do jogo para e ele só obedece até e.release():

const e = enemies.spawn("meu_mod:sucateiro", 120.5, 80.5);   // null no mundo Pacífico ou em água
e.moveTo(130, 80);            // anda (contorna o que bloqueia) e para lá
e.attackBuilding(b);          // ou attackPlayer(jogador), attackEnemy(outro); e.stop() fica parado
e.health = e.maxHealth;       // cura; e.damage(50, jogador) fere (caindo, a sucata vai para o jogador)
e.data.set("chefe", true);    // dados deste inimigo, salvos com o mundo; quando ele cai, vêm no onDefeated
enemies.onTick("meu_mod:sucateiro", 15, e => { /* a cada meio segundo, para cada um vivo */ });
enemies.onDefeated(d => { if (d.data?.chefe) world.dropItems(d.x, d.y, "iron_gear", 20); });

As ordens não vão no save: ao abrir o mundo, ele volta ao comportamento normal até o script mandar de novo (por isso vale mandar a ordem no onTick). Com "weight": 0 no JSON, o inimigo só aparece quando o script cria. O mod mecanica_exemplo tem um exemplo completo: o comando /ladrao chama um ladrão de engrenagens.

Animações: o .bbmodel pode ter quantas animações quiser. Sem script, pelo estado, no JSON da construção: "animations": { "working": "work", "idle": "parado", "noPower": "sem_energia" } (trabalhando — padrão work —, parada e sem energia); no do inimigo: "animations": { "walk": "andar", "idle": "respirar" }. Pelo script:

b.animate("abrir", { loop: false, speed: 1.5 });   // qualquer animação do modelo; b.animate(null) volta à do estado
b.pose("eixo", { spin: [0, 180, 0] });            // gira sempre (graus por segundo), sem custo a cada tick
b.pose("ponteiro", { rotation: [0, 0, 30] });     // pose fixa (graus) e/ou position [x, y, z]; b.pose("eixo", null) tira

As poses somam com a animação; mandar a mesma coisa de novo não custa nada (só vai aos jogadores quando muda).

Telas: o script descreve a janela com as peças do jogo e o jogo desenha com o visual dele (mesmas fontes, cores e escala). O jogador recebe só a descrição, nunca código.

ui.show(jogador, { id: "loja", title: "Loja", width: 460, building: b.id /* opcional: abre junto a janela da máquina */, body: [
  { type: "text", text: "Quantas placas?", color: "accent" },
  { type: "field", id: "qtd", value: "10" },
  { type: "row", children: [ { type: "button", id: "pedir", text: "Pedir", primary: true }, { type: "button", id: "fechar", text: "Fechar" } ] },
  { type: "bar", value: 0.4, text: "40%" },
] }, ev => {   // ev = { button, fields: { qtd: "10" }, closed, player }
  if (ev.button === "pedir") players.give(ev.player.id, "iron_plate", Number(ev.fields.qtd));
  if (ev.button === "fechar") ui.close(ev.player.id, "loja");
});

Peças: text (text, size, color), button (id, text, primary, disabled, tooltip), field (id, label, value, placeholder; Enter conta como clique com o id do campo), row (children), bar (value 0..1, text, color), icon (item, count, size), image (src: PNG da pasta do mod, width, height), list (items: texto ou { icon, text }, height), tabs (tabs: [{ title, body }]), graph (series: [{ values, color }], height), separator, slot (slot: o número do espaço, label, hint, color, size) e slots (from, count, columns, color). Cores: accent, danger, energy, dim, text ou #rrggbb.

Espaços de item na janela: numa janela com building (a construção dela), slot e slots mostram os espaços do baú da construção ("container" no JSON; o primeiro é o 0), ao vivo e arrastáveis como nos baús do jogo: arrastar, Ctrl + arrastar (metade), Shift + clique (vai para o inventário; no inventário, Shift + clique manda para a máquina). Com espaços, a janela do mod faz o papel da janela da máquina: a do jogo não abre junto e o inventário encosta nela. Quem decide se o item pode ir é o servidor (alcance e permissão, como sempre). Exemplo: a caixa de engrenagem do mecanica_exemplo ({ type: "slots", from: 0, count: 4, columns: 4 }). Mandar ui.show de novo com o mesmo id atualiza a janela (o que o jogador digitou continua). Também: ui.close(jogador, id), ui.toast(jogador, texto, cor) (aviso embaixo) e ui.hud(jogador, id, texto) (linha fixa no alto da tela; null tira).

Pesquisas e contratos: research.list() (cada uma com done, available, current, units, unitsDone, level, repeat, delivery, effect), research.current, research.select(id) (null = nenhuma), research.isDone(id), research.level(id), research.grant(id) (conclui e libera as receitas; infinita: +1 nível), research.progress(unidades) (na atual), research.bonus(efeito); contracts.list() (por região: contrato ativo, item, por minuto, segundos pedidos, ritmo atual, tempo mantido, posição na fila) e contracts.finish(região) (fecha o ativo no próximo tick, com as recompensas). Eventos: events.onResearch, events.onContract.

Efeito novo de pesquisa infinita: no JSON, "repeat": { "effect": "alcance", "perLevel": 5 } (qualquer nome com letras minúsculas, números e _ vira efeito do mod, meu_mod:alcance). O jogo só soma os níveis; o script aplica, ex.: const alcance = 8 + research.bonus("alcance") / 5;. Os efeitos do jogo continuam: mining_speed, crafting_speed, research_speed.

Clique na máquina do mod: construção com "script": true avisa o servidor quando alguém clica nela: buildings.onInteract("meu_mod:terminal", (b, jogador) => ui.show(jogador, {...})). Com "ownWindow": true no JSON, o clique abre só a janela do script (sem a janela padrão da máquina).

Ids de item e construção como no JSON: "base:iron_plate" (sem prefixo, vale o base). Trancado: sem arquivos fora de scripts/, internet ou acesso ao computador; um laço infinito (mais de 250 ms numa chamada), mais de 64 MB ou recursão sem fim desligam só os scripts daquele mod, com aviso. Erros aparecem no console do servidor com scripts/arquivo.js:linha:coluna. No servidor.json, "scripts": false desliga todos os scripts.

Modo desenvolvedor (Opções → Interface): F8 abre o console dos mods — mensagens e erros dos scripts, quanto cada mod gasta por tick, uma linha de JS para testar (mekzorio.players.list(), mekzorio.world.tile(0, 0)…) e Recarregar scripts (salve o .js e recarregue, sem fechar o mundo). F3 mostra os ids do que está na mira. No servidor (ou em rede, sendo administrador): /mods, /reload e /js <mod> <código> no chat.

Arte e som (por convenção de pastas)

Arquivo no mod Usado como
textures/items/<id>.png ícone do item, 16×16, estilo pixel art calmo
textures/resources/<id>.png, textures/terrain/<id>.png jazida e chão
models/<id da construção>.bbmodel modelo 3D da construção
sounds/<id da construção>_loop.wav som da máquina trabalhando, em laço; WAV mono de 16 bits
sounds/<nome>_1.wav, _2.wav… variações de um efeito; um mod carregado depois pode trocar um som do base com o mesmo nome

Nos modelos, 16 unidades valem 1 tile, e a frente fica para +X. O jogador tem ~27 unidades de altura, então as máquinas devem ser bem maiores que ele.

Os nomes das peças do modelo mudam como ele aparece no jogo:

Nome da peça Efeito no jogo
contém chimney, stack ou exhaust sai fumaça do topo da mais alta
começa com glow brilha com a cor da textura
começa com accent pega a cor do jogador

A animação chamada work toca enquanto a máquina trabalha.

Sem arte, o jogo usa a cor do campo color e um modelo simples. Dá para testar o mod antes de ter a arte.

Multijogador

Como no Minecraft Bedrock: quem entra num servidor com mods usa os mods do servidor só enquanto joga nele. O jogo compara um resumo (hash) de todo o conteúdo; se for diferente, procura cada mod na versão exata do servidor — na pasta daquele servidor (o que já baixou dele), nos seus mods ou nos do jogo. Se tem todos, entra direto. Se falta algum, aparece "Este servidor usa mods" com cada mod e de onde vem, e Baixar e entrar traz só os dados e a arte para a pasta daquele servidor (mods_servidores/<endereço>_<porta> na pasta do jogo). Os mods ligados nos seus mundos não mudam. Do servidor nunca vem código: os scripts dos mods rodam no servidor. Se a versão do jogo for diferente, não dá para baixar: atualize o jogo ou o servidor.

No servidor dedicado, em servidor.json:

{ "mods": [ "fornalha_tijolos" ], "modsDir": "mods", "shareMods": true, "scripts": true }

shareMods: false não deixa baixar os mods pelo jogo (aí cada um instala); scripts: false desliga os scripts dos mods (só os dados valem).

Mundos salvos

O save guarda a lista de mods. Ao abrir um mundo, o jogo ativa sozinho os mods dele, se estiverem instalados. Se faltar algum, ele avisa qual é.

Para testar rápido

scripts/jogar.sh -- --mods fornalha_tijolos     # ativa mods só nesta vez, sem mexer nas opções

Mapas em mods

Um mod pode trazer mapas em maps/<id>.json. Eles aparecem em Novo mundo → Começar de quando o mod está ativo. Os mapas que vêm com o jogo (o Mapa de teste) ficam em mods/base/maps/ e aparecem sempre; o jogo base não aparece na tela de Mods (ele não é um mod: está sempre ligado). O mapa não é um save pronto: é uma receita de montagem. Ao começar o mundo, o jogo gera o terreno pela seed, pinta o que o mapa pede e constrói tudo com as mesmas ações de um jogador — então ele sempre usa o conteúdo atual do jogo (e dos mods ativos). Exemplo completo: mods/base/maps/teste.json.

{
  "name": { "pt-BR": "Meu mapa", "en": "My map" },
  "description": { "pt-BR": "O que tem nele" },
  "mode": "creative",            // modo sugerido (career, creative ou sandbox); o jogador pode trocar
  "offset": [ -4, -4 ],          // posições contam a partir do ponto inicial + offset
  "terrain": [                   // retângulos pintados, na ordem
    { "from": [ 0, 0 ], "to": [ 20, 10 ], "terrain": "grass", "clearResource": true },
    { "from": [ 2, 2 ], "to": [ 4, 4 ], "resource": "iron_ore", "amount": 20000 }
  ],
  "build": [                     // na ordem; "_" é só anotação
    { "id": "pipe", "at": [ 5, 0 ], "to": [ 9, 0 ] },               // "to": uma linha/retângulo da mesma peça
    { "id": "assembler", "at": [ 10, 2 ], "rot": 0, "recipe": "iron_gear", "insert": { "iron_plate": 100 } },
    { "id": "requester_chest", "at": [ 14, 2 ], "requests": { "copper_plate": 200 } },
    { "id": "train_stop", "at": [ 0, 9 ], "rot": 1, "station": "Base" },
    { "vehicle": "locomotive", "at": [ 6, 10 ], "rot": 0, "insert": { "coal": 50 } },
    { "train": [ 6, 10 ], "schedule": [ { "station": "Base", "wait": "time", "seconds": 10 } ], "automatic": true }
  ],
  "showroom": { "at": [ 0, 30 ], "width": 60 }   // opcional: uma de cada construção e veículo carregados
}
  • rot: 0 leste, 1 sul, 2 oeste, 3 norte. Ids sem mod: são do jogo base.
  • mode / filter: braço ("auto", "fuel", "input" + filtro de item), bomba de vagão ("fill" encher, "empty" esvaziar) e divisor ("left" ou "right": por onde sai o item do filter; o resto sai pelo outro lado).
  • wait do roteiro: time (com seconds), full ou empty.
  • O que não couber (lugar ocupado, id que não existe) vira um aviso no log; o resto do mapa é montado.
  • Para conferir um mapa sem abrir o jogo: dotnet run --project src/Automacao.Tools -- mapa-teste (monta o mapa de teste do jogo base, roda 40 s e diz o que funcionou).
  • Para ver no jogo, com fotos de cada área: --novo-mundo 2026 --modo criativo --mapa-mod base/teste --auto-kit --capturas PASTA (o piloto anda pelas áreas e salva uma imagem de cada).
  • Dicas de montagem: o rot também gira as portas dos baús (um baú com "rot": 1 solta para o sul, direto na entrada de cima de uma montadora); um baú com vários itens só solta o da primeira pilha, então para alimentar uma máquina com vários ingredientes de um baú só use um braço (ele só pega o que a máquina aceita). A câmera olha do sul: o que fica logo ao norte de uma máquina alta some atrás dela, então ponha baús e braços a oeste, a leste ou ao sul.
  • Ainda não dá para configurar filtro ou modo do braço pelo mapa (só no jogo).

O mapa de teste (vem com o jogo) tem: energia (vapor, carvão com baús de reserva, sol, baterias, vento), mineração → fundição → montadora, esteiras, drones, petróleo → plástico e combustível sólido, trem em linha fechada, pesquisa (pacotes vermelho e verde → laboratórios), o começo a carvão (mineradora e fornalha de pedra), aço, tijolos e armazém, a cadeia da eletrificação (lítio, vidro, silício, bateria, circuito avançado, pacote azul), os níveis de montadora (pacote roxo de 6 ingredientes na montadora 3, braço rápido) e a vitrine. No criativo tudo já vem pesquisado, então os laboratórios não aceitam pacotes: eles ficam esperando no baú ao lado.
